# 产品教程文档工作流

当目标不是单张截图标注，而是一套“截图 + 标注 + Markdown 教程文章”时，使用这份流程。

## 目录

- 触发场景

- Markdown 图片路径规则

## 触发场景

- 用户要求产品教学图、教程截图、使用教程、操作手册或带截图的 Markdown 文档。
- 用户希望从普通用户视角解释产品，而不是只标注已有图片。
- 用户希望先规划、再截图、再写文档，避免随机点选和零散截图。

## 核心原则

- 教程图不是发现式截图。先规划学习路径，再截图。
- 演示数据要服务教学目标。没有数据支撑的空页面通常不适合作为教程主图。
- 数据型截图必须先确认数据丰富度。报表、图表、统计卡片、Token 消耗、趋势分析、状态列表和看板不能用稀疏数据硬撑教程。
- 每张图的文字标签和可见标记必须能在正文中逐条说明。单标注页面可以不显示编号，但正文仍要解释该动作或结果。
- 截图不是正文的替代品。正文必须说明用户要看哪里、能做什么、怎么判断。
- 标注图、QA 文件和教程文档要作为一套工程化交付物，而不是散落图片。

## 推荐流程

1. 建立产品能力地图。
   - 读取本地代码、README、已有产品文档、配置和路由结构。
   - 梳理用户能完成的主要任务、关键页面、数据来源和状态分类。
   - 只依赖本地证据；如果需要项目外技术事实，再按当前环境规则使用外部文档工具。

2. 规划教程测试路径。
   - 先确认适用对象、前置条件、学习目标和完成后的用户结果。
   - 写 `tutorial-test-path.md`。
   - 每个截图点要包含：页面、用户目标、需要出现的数据、截图前置状态、是否需要标注。
   - 路径应覆盖入门、核心操作、能力配置、自动化或数据洞察，以及必要的检查页面。

3. 构建演示数据。
   - 写 `tutorial-data-plan.md`。
   - 优先使用隔离目录、测试账号或临时 profile，避免污染真实数据。
   - 数据至少覆盖：多角色、多状态、数量差异、时间差异、成功/待处理/异常等对教学有帮助的状态。
   - 数据型截图先做门禁判断：当前数据是否能展示趋势、分类、对比、Top 项、状态分布和异常/空态。
   - 数据不足时先构造演示数据，再进入截图；不能为了赶进度使用空报表、单条记录或无法体现差异的数据。
   - `tutorial-data-plan.md` 至少记录：每张数据截图的教学目标、已有数据状态、补充数据范围、隔离方式、清理/还原方式。

4. 截图并验证原始图。
   - 原始图放入 `raw/`。
   - 截图后立刻打开原图检查：页面是否正确、数据是否完整、弹窗或更新提示是否遮挡、像素是否真实刷新。
   - 数据型截图还要确认：关键数值不为空、图表有可解释趋势、分类或 Top 列表足够丰富、状态不是单一值。
   - Electron 和浏览器调试场景要防止“无障碍树或 DOM 已变化，但系统截图仍是旧页面”的错图。

5. 标注计划。
   - 每张图只保留完成当前教学目标所需的标注，通常 1-5 个；不要为了版式凑数量。
   - 一个文字标签或标记只解释一个主要教学点。
   - 单个教学点默认不显示 `1`；真实顺序使用数字；并列或互斥入口使用 A/B。
   - 操作页使用动作型文案，信息页使用阅读、核对或查看结果类文案。
   - 复杂区域用大框，关键按钮用小框；不要为了显得完整而把整屏都框住。
   - 坐标必须来自原始截图像素；不要直接套用 DOM、CSS、无障碍树、缩放预览或裁切图坐标。
   - 标注框按完整视觉区域框选，给组件边界、图表轴、状态徽标和按钮文字留出安全边距。
   - 文字标签按最少遮挡原则选择锚点；右下是常用候选，但标题、星号、关键文字、数据、图例、按钮和状态优先受保护。
   - 坐标难以判断时先生成 100px 网格；网格只用于定位，不强制吸附框位。
   - 标注 JSON 放入 `plans/`，文件名和原图一一对应。

6. 标注渲染和 QA。
   - 标注图放入 `annotated/`。
   - 每张图的 QA 放入 `qa/<image-id>/`。
   - 必看完整标注图、每张图的 `qa-contact-sheet.png`、`review.json` 和 `qa-summary.json`。
   - 额外生成 `qa/full-contact-sheet.png`，检查整套图是否存在标签贴线、框线共线、视觉节奏不一致或局部遮挡。
   - 数据型截图额外检查：数据是否仍然足够讲清页面能力；如果图表空、趋势弱、分类少或状态单一，回到演示数据步骤返修。
   - 标注偏移、框选不完整、标签遮挡、交叉贴线和视觉拥挤都是 blocker；必须改计划 JSON 后重跑。

7. 编写教程文章。
   - 优先复制 `templates/tutorial-document.md` 作为起点。
   - 使用可重复的截图步骤块，不要为了模板硬凑 5 张图或固定数量的标注。
   - 每张图后按实际标签语义写说明；存在数字或 A/B 时，正文标记必须和标注计划一一对应。
   - 单标注免编号时，用一段动作或结果说明直接解释图片，不要在正文里重新制造编号。
   - 文案写用户能做什么、看到什么、下一步怎么判断。
   - 不要在正文暴露实现细节，除非用户要求面向开发者。
   - 本地交付时，优先确认 Markdown 预览器能显示图片；如果相对路径不显示，改用绝对路径。
   - 成品交付前检查是否残留未填的双花括号占位符。

8. 交付说明。
   - 写 `README.md`，说明最终教程、标注图、原始图、计划文件、QA 文件和已知未采用截图。
   - 如果某些页面因截图不稳定、数据不足或遮挡问题未采用，要说明原因。
   - 在教程正文或 README 中保留截图资产清单，便于后续返修和迁移。

## Markdown 图片路径规则

- 面向本地 Codex 或桌面预览交付时，优先使用绝对路径，确保图片可显示。
- 面向仓库或可迁移文档交付时，可使用相对路径，但必须实际打开预览确认。
- 如果用户截图反馈图片只显示占位符，先检查 Markdown 图片路径解析，而不是先怀疑图片损坏。
- 交付说明中要写清楚：交付场景、图片路径模式、图片显示校验结果。

## 教程正文检查清单

- 标题说明产品名称和教程目的。
- 开头说明适用对象、前置条件、学习目标和完成后能做什么。
- 每张图都有可读的 Markdown 图片 alt 文本。
- 每张图后面的说明和图中文字标签数量、顺序、语义一致。
- 数字或 A/B 标记存在时，正文标记必须一一对应；单标注免编号时不强加序号。
- 每条说明只解释一个主要教学点，不混写多个动作。
- 正文写用户动作、可见结果和判断方式，不写内部实现细节。
- 成品文档没有残留未填的双花括号占位符。

## 资产清单与弃用截图记录

- 教程交付包必须能追溯每张最终图的来源：`raw/`、`plans/`、`annotated/`、`qa/`。
- 推荐在教程正文或 README 中维护截图资产清单，字段包括：教程步骤、最终标注图、原始图、标注计划、QA 文件、采用状态。
- 未采用截图也要记录原因，例如像素未刷新、数据不足、弹窗遮挡、标注密度过高或学习路径不成立。
- 如果后续需要迁移到仓库、知识库或发布平台，先调整图片路径，再打开目标预览环境做显示检查。

## 数据型截图门禁

以下页面截图前必须先过数据门禁：

- Token 消耗、费用、用量、报表、趋势、统计卡片、仪表盘、状态看板。
- Agent 列表、任务列表、日志列表、渠道状态、技能分配、执行记录、异常中心。
- 任何用户需要通过数据判断“当前是否正常、哪里最多、趋势如何、状态有什么差异”的页面。

数据丰富度最低要求：

- 时间维度：至少能看出多个时间点或时间范围；趋势图不要只有一个点。
- 分类维度：至少有多个分类或主体，例如多个 Agent、多个渠道、多个技能、多个任务类型。
- 状态维度：尽量覆盖正常、待处理、异常、离线、成功、失败、空态等对教学有意义的状态。
- 数量维度：要有明显差异，能支持“最多、最少、总量、平均、Top 项”等说明。
- 解释维度：截图下方的标签说明能逐条解释图中的数据，而不是只能描述空壳 UI。

数据不足时的处理：

- 优先使用隔离演示数据，不污染真实用户数据。
- 构造数据前先确认数据来源和安全边界；不要写入生产账号、真实客户数据或不可回滚目录。
- 构造数据后重启或刷新产品，确认页面真实读取到了新数据。
- 截图后把演示数据覆盖范围写入 `tutorial-data-plan.md`，必要时写清理/还原步骤。
- 如果无法安全造数，记录为未采用截图，改用文字说明或更换页面。

## 本次 MotiClaw 案例沉淀

- 先从代码确认应用数据目录、Agent 注册表、技能部署、自动任务和 Token 分析的数据来源。
- 使用隔离演示数据覆盖 4 个 Agent、多个状态、多个渠道、技能分配、定时任务和消耗趋势。
- Token 消耗分析这类报表截图，如果初始数据太少，要先构造更丰富的时间序列、Agent 分类、成本和 Top 项，再截图。
- 系统设置这类密集页面要分上半部分和下半部分截图，标注应按完整设置区域框选，避免标题和图注错位。
- 第二轮 QA 修复编号贴线、红框共线、按钮文字压线、图注错位和框选偏移问题。
- Markdown 中最初使用相对路径导致预览不显示，最终改为绝对路径并校验文件存在。
